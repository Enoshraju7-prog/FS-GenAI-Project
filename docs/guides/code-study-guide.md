# Code study guide

A two-day walkthrough of every file we wrote, ordered by **data flow** rather than
alphabetically — a filing enters as HTML on the left and leaves as a cited answer on the
right, and each session follows one hop of that journey.

Scope: ~4,550 lines of backend (`app/` + `ingest/`), ~1,400 lines of frontend
(excluding shadcn primitives in `components/ui/`), ~1,600 lines of tests.

`components/ui/*` is generated by the shadcn CLI — read it only when a specific
behaviour puzzles you, never front to back.

**How to use this:** for each file, read the code first and try to answer the question in
the "Be able to answer" column *before* reading my explanation. The questions are the
point; the file list is just scaffolding.

## Day 1 — Backend

### Session 1 · Foundations (~30 min, 200 lines)

Read these first; everything else assumes them.

| File | Lines | Be able to answer |
|---|---|---|
| `app/config.py` | 78 | Why does *all* env access go through one Settings object? What breaks if a module calls `os.getenv` directly? |
| `app/main.py` | 31 | What order do things initialise in? Why is `configure_logging()` called before `FastAPI()`? |
| `app/logging.py` | 34 | Why `PrintLoggerFactory` over stdlib logging? What does `bind()` give you that f-strings don't? |

**The big idea:** two different database paths coexist — SQLAlchemy for raw
pgvector/tsvector SQL, and the Supabase client for anything that must respect RLS.
Understand *why* before moving on.

### Session 2 · Ingestion, part 1: the table extractor (~90 min, 600 lines)

`ingest/sec_tables.py` is the hardest and most interesting file in the project. Budget
real time for it.

Read in this order — not top to bottom:

1. `_TreeParser` + `_Node` + `_RawCell` (lines ~96–140) — a streaming HTML parser building a DOM tree.
2. `extract_sec_tables` (~142) — the orchestrator. Skim, then come back.
3. `_raw_rows`, `_cell_nodes`, `_positive_int` — how colspan is expanded into cells.
4. `_is_meaningful` — the layout-table filter.
5. `_normalize_rows` and its three shapes: `_normalize_sales_change_table`, `_normalize_simple_table`, `_normalize_schedule`.
6. `_consume_amount` / `_consume_change` — how `$` `209,586` in two cells becomes `$209,586`.
7. `_table_context` — how a title and units are inferred from surrounding prose.
8. `_facts` / `InlineFact` — inline XBRL capture.

**Be able to answer:**
- Why does a SEC table have ~30 columns when it visually has 6?
- Why does `table_index` count *kept* tables rather than raw `<table>` position — and what bug did that cost me when I first diagnosed this?
- Why does `_looks_like_schedule_row` require *exactly one* amount? What breaks if you loosen it?
- What is an `InlineFact` and why is it the accuracy ceiling for this project?

**Experiment:** run the extractor over one filing and print any table whose columns look
wrong. Then open that table in the source HTML and work out why.

## After the study: improvement backlog

Grounded in what we already know is unfinished — start here rather than inventing work.

**Correctness / completeness**
1. Finish the Phase 8 items never completed: smoke-test the 10 client-brief questions, and measure time-to-first-token.
2. Tables still dropped by `_normalize_rows` — notably "Purchases of Equity Securities" (share repurchase, a real financial table). Warnings are printed; go read them.
3. Use the inline XBRL facts. They're parsed and stored but never used. Validating each extracted number against its filed XBRL value is the single biggest accuracy upgrade available.

**Retrieval quality**
4. Row-level chunks were dropped for storage reasons. Verify precise numeric lookups ("iPhone net sales in FY2025") didn't regress — if they did, reintroduce row chunks *without* the duplicated metadata blob.
5. Tune `top_k` / `candidate_k` against the 10 brief questions rather than by intuition.

**Engineering**
6. No frontend tests by project policy — so the type contract between `schemas/chat.py` and `chat-types.ts` is maintained by hand. Consider generating one from the other.
7. `main` is behind `development`. Anyone opening the GitHub link lands on old code.
8. Bundle is ~1 MB (297 KB gzipped) with no code splitting.

**Product**
9. No "no filing evidence found" state when an answer comes back with zero citations.
10. Thread titles auto-set once and never update; the header can show a stale title.
